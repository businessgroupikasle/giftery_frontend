# Product Customization Plan

## Decisions and boundaries

- Include the sibling `D:\Giftery\ecommerce-project\backend` repository and frontend. Preserve the existing design and normal purchase flows.
- Allow authenticated customers to create visual mockups for all products. Require sign-in before editing and save an account-owned draft so it survives refresh and navigation. A generic overlay is not a verified printable area; label the preview accordingly. Do not generate or claim a print-ready file without verified product-specific specifications and tested output.
- Current products have no structured variant selector or print-area configuration. Show only actual available variants/options; do not invent them. Use real gallery images, and do not claim front/back meaning where it is unknown.

## Implementation workflow

1. Establish a baseline in both repositories: inspect current changes, migrations, scripts and existing product/cart/order paths; run relevant available tests. Select a real existing product and image for integration testing. Confirm database, authentication, private file storage and test payment availability; record unavailable prerequisites rather than substitute mocked tests for a real flow.
2. Define a versioned customization snapshot: product ID, actual variant/options if present, selected product image, asset IDs, text/font/color, normalized placement/size/rotation, preview asset ID and metadata. Validate bounded values and supported fonts. Persist separate draft, cart and order snapshots, with immutable order data; never store raw image bytes in database fields.
3. Backend: add migrations and models for user-owned artwork and per-product drafts, plus nullable customization snapshots on cart and order items. Replace the cart's `(cartId, productId)` uniqueness with line identity that distinguishes designs while retaining ordinary item behavior. Backfill existing rows safely, and ensure quantity changes and removal target the correct owned line. Enforce stock across lines for the same product and preserve existing cart data.
4. Backend: use existing local disk storage with a separate non-public location and authenticated upload/read endpoints. Validate file signatures, decoding, dimensions, size and allowed PNG/JPEG formats on the server; limit decompression and reject malformed content. Associate every file with its owner, verify ownership and product/draft associations on every reference, and restrict order artwork access to the owning customer and authorized staff. Implement lifecycle cleanup for orphaned temporary files without deleting assets referenced by carts or orders. Do not expose private files via existing public `/uploads` routes.
5. Backend: extend cart and order validation, services and responses to preserve snapshots and preview references through authenticated cart fetch, checkout, order creation and order detail. Enforce item ownership on cart mutations and referenced assets. Keep old non-customized requests valid. Ensure direct Buy Now does not erase an unrelated cart. Restrict changes to those required for this workflow and cover migrations and authorization with integration tests.
6. Frontend: extend `src/pages/Product/index.jsx` and `Product.module.css`, reusing existing controls and styling. Add a sign-in-gated customization panel with upload, replace/remove, text styling, draggable position, scale and rotation, reset, and undo/redo if practical. Render overlays directly on the selected real product image, using coordinates normalized to its displayed content for responsive resizing. Support zoom and gallery-angle selection without claiming unverified product sides or printable regions. Show upload/save failures and do not permit purchase of unsaved or failed assets.
7. Implement authenticated draft load/save with debouncing, explicit save/error status, and race-safe handling of uploads and edits. Restore the selected design after refresh/navigation; use authenticated fetch/blob URLs for private assets and revoke object URLs. Produce and privately store a preview image using the same image and overlay transform; handle CORS/image loading failures explicitly rather than silently submitting an incorrect preview.
8. Update `src/store/slices/cartSlice.js`, cart and checkout views, and customer/admin order-detail views only as necessary to display the correct private preview and preserve customization metadata. Use stable cart-line IDs, not product IDs, for update/remove. Keep ordinary products, pricing, stock, authentication, quantities and existing API consumers working. Handle Buy Now refresh safely without relying solely on transient navigation state.
9. Add focused unit and integration coverage for normalized transforms, persistence, multiple designs of the same product, ownership, invalid/oversized images, migration of existing carts, failed uploads and order snapshots. Extend Playwright product/cart/checkout/order tests for editing and preview; keep mock-based UI tests distinct from live backend tests. Run frontend lint, build, unit and relevant Playwright tests, plus backend regression and integration tests available in the environment.
10. Exercise the requested end-to-end checklist against an existing product and real test services: upload actual artwork; move, scale, rotate and style text; refresh; add to cart; inspect preview and metadata; place a test order; verify customer and staff order details and cross-user denial. Test desktop and mobile, normal non-customized purchases and stock limits. Report exact files changed, commands/results and any untested prerequisites; do not label the result production-ready without real output verification.

## Risks and release gates

- Existing checkout trusts client pricing and totals, has stock/product validation weaknesses, and the payment service accepts mock or missing-signature verification in inspected paths. These pre-existing issues are production blockers independent of the mockup feature; do not imply they are resolved or validate payment using mocked success. If they prevent a safe real test, report the blocker and keep payment remediation separately scoped.
- Existing upload endpoints are publicly served and not owner-scoped; do not reuse them for customer artwork. Local storage must be persistent across backend restarts/deployments for the target environment.
- Product images may not be same-origin or canvas-readable. If preview generation cannot access the real image safely, expose an actionable error and do not fabricate a preview.
- No production dimensions, bleed, DPI or verified placement currently exist. Mockups are visual only; production-file generation is out of scope until those specifications are supplied and output is tested.
